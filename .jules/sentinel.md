## 2024-05-18 - Fix Hardcoded Plaintext Password Storage
**Vulnerability:** Shift group passwords were being stored in plaintext in the Firestore database (`groupDoc.data().password`) and directly compared with plaintext payloads during authentication (`request_join`). This is a critical security vulnerability as any database leak exposes all group passwords.
**Learning:** When adding hashing algorithms to legacy codebases, using a simple heuristic like `.includes(":")` to determine if a stored string is a hash vs a legacy plaintext password is too broad and can inadvertently lock out users who used colons in their valid passwords.
**Prevention:** Always use a distinct, cryptographic signature prefix (like `$scrypt$`) when creating hashes so they can be unambiguously identified when implementing fallback/upgrade logic (`storedPassword.startsWith("$scrypt$")`).
## 2026-05-18 - Fix Plaintext Password Storage and SyntaxError
**Vulnerability:** Shift group passwords were being generated/stored in plaintext in the Firestore database (`groupDoc.data().password`) and directly compared with plaintext payloads during authentication (`request_join`). The migration code to switch this to `scryptSync` hashes was left in a broken, half-implemented state throwing a fatal SyntaxError (`Identifier 'newGroup' has already been declared`), crashing the backend.
**Learning:** Merging complex security refactors (like moving from plaintext to salted hashes) without verifying intermediate states can introduce critical execution failures (SyntaxErrors) alongside the logic bugs, breaking both security and application functionality simultaneously.
**Prevention:** Always verify script execution via CLI (e.g., `node backend/index.js`) to catch duplicated declarations or syntax breakage introduced during migration logic before pushing partial refactors to production.
## 2024-10-03 - Fix Invalid Scrypt Hash Prefix Breaking Auth Migration
**Vulnerability:** When implementing a migration from plaintext passwords to scrypt hashes, the new hashes were stored with the incorrectly formatted prefix `$scrypthash:salt` instead of `$scrypt$hash:salt` (due to missing a `$` sign in the template literal `\`$scrypt\${hash}\``). Because the authentication flow checked for `startsWith("$scrypt$")`, these newly hashed passwords fell back to plaintext comparison, permanently breaking authentication for new users.
**Learning:** Security validation logic (like prefix matching) must strictly align with the generator logic. A simple typo in a template literal entirely bypassed the intended hash verification, rendering the security control ineffective.
**Prevention:** Always write dedicated unit tests specifically verifying that newly generated hashes can be successfully parsed and validated by the existing authentication logic, rather than just testing that a hash was generated.
